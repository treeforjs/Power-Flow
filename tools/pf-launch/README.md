# pf-launch v1.1

Portable launcher for Power-Flow runs (coupled pilot plan, section 7). The number of cores, the exact
cores and the GPUs are chosen per run with flags. No code or wrapper script changes between runs or
machines; everything machine-specific lives in one site file per machine.

```
pf-launch [--site SITE.json] [--cores N|auto | --cpus LIST] [--gpus none|auto|LIST|count:N]
          [--ranks-per-gpu K] [--cores-available] [--wait] [--launcher auto|exec|mpirun|srun]
          [--execution site|host] [--prefix CMD] [--dry-run] [--json] [--receipt PATH]
          -- PROGRAM ARGS...
pf-launch --detect [--site PATH] [--force]
```

| File | Purpose |
|---|---|
| `pf_launch.py` | The launcher (Python 3.9+, standard library only; runs under the system python and the frozen root's python). |
| `pf-launch` | Shell shim: `exec python3 pf_launch.py "$@"` (symlink it into `PATH`). |
| `sites/zenobia.json` | Workstation site file: generated by `--detect`, then completed by hand. |
| `tests/test_pf_launch.py` | Unit tests with fake topologies, GPU lists and probes (no launches). |
| `validation/rank_probe.py`, `validation/mpi_probe.c` | Placement probes used for the real-launch validation. |

## Workstation (zenobia) examples

Policy on zenobia: physical cores 0-5 belong to the Spheral work, permanently; Power-Flow uses physical
cores 6 and 7 (logical CPUs 6/14 and 7/15). The site file reserves cores 0-5 unconditionally. Runs go
through the frozen root (`run-frozen`) at nice 15. Identity admission is strict, and the leases are the
existing `pic-profile` lock files.

```sh
pf-launch --cores 2 --gpus 0 -- ./prog           # ranks 0,1 on CPUs 6,7; rank 0 gets the RTX 3080 Ti, rank 1 none
pf-launch --cpus 6-7 --gpus none -- ./prog       # same cores, CPU-only (CUDA_VISIBLE_DEVICES= for both ranks)
pf-launch --cpus 6 --gpus none -- ./prog         # one rank on CPU 6, plain exec (no mpirun)
pf-launch --cores auto -- ./prog                 # every free Power-Flow core (6-7 unless a lease is held)
pf-launch --cores 1 --gpus none --wait -- ./job  # any free core (6, else 7); poll until one is free
pf-launch --dry-run --cores 8 -- ./prog          # refuses (exit 75): only cores 6-7 are available
pf-launch --dry-run --cores 8 --cores-available -- ./prog   # accepts 2 ranks on 6-7
pf-launch --cpus 6,14 -- ./prog                  # refuses (exit 64): 6 and 14 are SMT siblings
pf-launch --execution host --cpus 6 -- ./prog    # bypass run-frozen (still pinned, niced, leased)
pf-launch --cpus 6-7 --gpus none --launcher exec --wait -- cmake --build build   # one process on 6,7 (builds)
```

`--dry-run` prints the resolved plan: identity checks, reservations and probe results, the per-rank
CPU, SMT siblings and `CUDA_VISIBLE_DEVICES`, nice, the lease files in acquisition order and the exact
argv. It exits 0 only if the run could start now. A refusal exits with the refusal's code. A valid plan
whose leases are held elsewhere exits 75: with `--wait` it ends in `result WAIT`, naming the lock files
a real run would block on.

### Interim helpers this replaces

`/home/treefor/projects/runtimes/core-lease-20261030/any-core.sh` and `both-cores.sh` are superseded once
pf-launch is adopted. pf-launch keeps their semantics:

| Helper | pf-launch equivalent |
|---|---|
| `any-core.sh [--wait] CMD` | `pf-launch --cores 1 --gpus none [--wait] -- CMD` (tries core 6 then 7, `PF_CORE` exported) |
| `both-cores.sh CMD` | `pf-launch --cpus 6-7 --gpus none --launcher exec --wait -- CMD` (leases 6 then 7, `taskset 6,7`, `MAKEFLAGS=-j2`, `CMAKE_BUILD_PARALLEL_LEVEL=2`) |

The lease files, the flock(2) lock type, the ascending acquisition order and nice 15 are the same, so
the helpers and pf-launch exclude each other correctly while both are in use. Two differences: pf-launch
runs through the frozen root unless `--execution host` is given, and it writes a receipt.

## 64-core RTX PRO 4000 Blackwell station

```sh
cd pf-launch-v1.1-20261030
./pf-launch --detect                      # writes sites/<hostname>.json from /sys, NUMA and nvidia-smi
$EDITOR sites/<hostname>.json             # see "Completing a detected site file"
./pf-launch --dry-run --cores 16 --gpus 0 -- ./prog
./pf-launch --cores 16 --gpus 0 -- ./prog          # 16 ranks on 16 physical cores; rank 0 on the GPU
./pf-launch --cores 63 --gpus none -- ./prog       # CPU-only, 63 ranks
./pf-launch --cores 8 --gpus 0 --ranks-per-gpu 2 -- ./prog   # ranks 0 and 1 share GPU 0; ranks 2-7 CPU-only
```

A detected site file loads and plans without edits: record-only identity, no reservations, nice 0,
leases under `~/.local/state/pf-launch/leases/`, plain host execution. With `--cores N` the cores are
taken by NUMA node and then by core number, so a 2-node Threadripper fills node 0 first. Put the cores
nearest the GPU first in `core_preference` (each GPU's `numa` field from `--detect` gives its node).
Runtime kernels must select the architecture from the device (sm_120 there, sm_86 on zenobia). The
receipt records each selected GPU's `compute_cap`.

### Completing a detected site file

| Key | Meaning |
|---|---|
| `nice` | Nice level for every rank and for mpirun (0-19; never lowered below the caller's). |
| `default_gpus` | `--gpus` default (`auto` per the plan; `none` on a CPU-only site). |
| `core_preference` | Cores tried first by `--cores N` / `auto`, e.g. `[6, 7]`; the rest follow by NUMA node, then core. |
| `reserved_cores` | `{"cores": [...], "reason": "..."}`: never used (zenobia: 0-5). |
| `reserved_gpus` | Same for GPUs (index or UUID). |
| `reservations` | Probes: `{"name", "cores", "gpus", "probe": {"argv", "timeout_s", "require_paths", "busy_regex", "free_regex"}}`. Reserved when a busy line matches. Free only when the probe exits 0, every required path exists and a line fully matches `free_regex`. Anything else (error, timeout, missing path, unrecognized output) counts as reserved. |
| `leases` | `core_path` (`{core}` = lowest logical CPU of the physical core), `core_overrides`, `gpu_path` (`{uuid}`, `{index}`), `gpu_extra` (additional lock files per GPU UUID). |
| `launcher` | `mpirun`, `mpirun_args`, `srun`, `srun_args`, `srun_in_allocation`, `nvidia_smi`, `wrapper_python`. |
| `execution` | `kind` = `host`, `frozen-root` or `container`; `prefix` (command placed before the program); `mpi_inside_prefix` (mpirun runs inside the prefix, as with run-frozen); `wrapper_python` (python inside the prefix); `root` and `manifest` for a frozen root; `image`, `image_digest`, `hash_image` for a container. |
| `environment` | `set` / `unset` applied to every rank (the thread variables cannot be overridden). |
| `identity` | `policy` = `strict` or `record-only`; `record` = expected `kernel_release`, `nvidia_driver_version`, `nvidia_srcversion`, `gpu_uuids`, `cpu_model`, `frozen_root_manifest_sha256` (null = not checked). |
| `receipt_dir` | Directory for receipts when `--receipt` is not given (default `./pf-launch-receipts`). |

Core numbers in site files and lease names are the lowest logical CPU of each physical core, taken from
`thread_siblings_list`. On zenobia, core 6 is CPUs 6 and 14; on the station, core K is CPUs K and K+64.

## Slurm cluster

Generate the site file on a compute node (`pf-launch --detect --site sites/cluster.json`), then set
`identity.policy` to `record-only` (or strict per node type) and `execution` to a container:

```json
"execution": {"kind": "container", "prefix": ["apptainer", "exec", "--nv", "/shared/images/power-flow.sif"],
              "mpi_inside_prefix": false, "image": "/shared/images/power-flow.sif",
              "image_digest": "sha256:...", "hash_image": false}
```

```sh
#!/bin/sh
#SBATCH --nodes=2 --ntasks-per-node=32 --cpus-per-task=1 --gpus-per-node=1 --time=02:00:00
pf-launch --site sites/cluster.json --gpus auto --receipt "$SLURM_SUBMIT_DIR/receipt-$SLURM_JOB_ID.json" -- ./prog
```

Inside an allocation (`SLURM_JOB_ID` set) pf-launch does not pick cores. It runs
`srun --ntasks=N --cpus-per-task=1 --cpu-bind=cores --ntasks-per-core=1 --kill-on-bad-exit=1` with N =
`SLURM_NTASKS` (or `--cores N` <= `SLURM_NTASKS`; `--cores-available` shrinks a larger request). `--cpus`
is refused there. On each node, rank `SLURM_LOCALID` gets entry `SLURM_LOCALID // K` of the step's
visible GPUs as `CUDA_VISIBLE_DEVICES`; ranks beyond the GPU count get it empty, and `--gpus none` empties
it for all ranks. Integer `--gpus` entries index the step's visible GPU list. Site reservations and
leases are not used, because the scheduler owns the allocation. The receipt directory must be on a
shared filesystem so that per-rank reports from all nodes reach the receipt. Check the cluster's srun
binding with one `--dry-run` and one short run; the receipt shows each rank's observed affinity and warns
if two ranks on one node share a physical core.

## Inside a SimQueue allocation (new in 1.1)

When `SIMQ_JOB_ID` is set together with `SIMQ_CPU_LIST` and/or `SIMQ_GPUS` (SimQueue 0.6 exports all of
them for every job), pf-launch treats the job as an allocation, the same way it treats a Slurm allocation:

- **Cores** come from `SIMQ_CPU_LIST` (one logical CPU per allocated physical core). `--cores auto` (the
  default) runs one rank per allocated CPU, `--cores N` takes the first N, `--cores-available` shrinks a
  larger request, and `--cpus LIST` must name CPUs inside the allocation (exit 75 otherwise). pf-launch picks
  no cores of its own and does not evaluate the site's static reservations or probes: the queue decided.
- **GPUs** come from `SIMQ_GPUS` (UUIDs; empty means no GPU). `auto` uses the allocated GPUs, a list or
  `count:N` must stay inside the allocation (exit 75 otherwise), `none` empties `CUDA_VISIBLE_DEVICES`.
- **Leases are not taken.** The queue's job unit already holds the core and GPU lease files for the job's
  lifetime; taking them again would block on itself (pf-launch 1.0 refuses with exit 75 inside a SimQueue
  0.6 job for exactly this reason).
- **Launchers** are unchanged (exec for one rank, mpirun for several); srun is not used.
- The receipt records the allocation under `selected_cores.simqueue` (the `SIMQ_*` variables).
- `SLURM_JOB_ID` takes precedence: inside a real Slurm allocation the Slurm path is used. SimQueue does not
  export `SLURM_*` variables, so the two cannot be confused.
- A SimQueue 0.5 job (`SIMQ_CPU_LIST` but no `SIMQ_GPUS`) gets its cores from the allocation and selects and
  leases GPUs locally, as before.

```sh
simq submit -p powerflow -c 2 --gpus 1 -t 4:00:00 -- pf-launch --gpus auto -- ./prog   # ranks on the 2 allocated cores
simq submit -p powerflow -c 1 -- pf-launch -- ./prog                                   # one rank, CPU-only
```

The zenobia site file's `simqueue-active` probe now calls the SimQueue 0.6 runtime.

Tests: `tests/test_simqueue_allocation.py` (fake topology and leases). The SimQueue 0.6 suite additionally
runs pf-launch 1.1 inside a real job unit (`PfLaunchInsideAllocationTests`) and shows that 1.0 refuses there.

## Behaviour

- **Cores.** `--cores N` takes N free physical cores; `--cores auto` (the default) takes every free one.
  `--cpus LIST` names logical CPUs, one rank each, in the listed order (rank 0 = first entry); it is
  refused if two entries are SMT siblings (per `thread_siblings_list`). Each rank is pinned to exactly one
  logical CPU (for `--cores`, the core's lowest CPU). The sibling thread is left idle, never given to
  another rank.
- **Refusal policy.** A core is unavailable if it is reserved (static list or probe), outside the
  process's cgroup cpuset, or leased by another process. `--cores N` with fewer than N available refuses
  with exit 75 and names the reservations and leases. `--cores-available` accepts fewer (at least one).
  `--wait` waits only for leases: with `--cpus` or a GPU list it blocks on the named lock files in
  order; with `--cores N` it re-plans every 3 s until enough cores are free. Reservations are never waited
  for.
- **GPUs.** `none` gives every rank `CUDA_VISIBLE_DEVICES=` (empty). `auto` uses the free GPUs, at most
  `ceil(ranks / K)` of them, and continues CPU-only if none is free. A list (`0`, `0,1`, `GPU-…`, mixed)
  names GPUs by `nvidia-smi` index or UUID: a bare integer is an index, so `--gpus 0` means GPU 0, not
  zero GPUs. `count:N` takes any N free GPUs. Rank r uses GPU `r // K`, where K is `--ranks-per-gpu`
  (default 1: one solver rank per GPU, starting with rank 0, the coordinator). Each rank receives the
  GPU's UUID in `CUDA_VISIBLE_DEVICES` plus `CUDA_DEVICE_ORDER=PCI_BUS_ID`. More GPUs than the ranks can
  use is refused.
- **Per-rank environment.** `OMP_NUM_THREADS=OPENBLAS_NUM_THREADS=MKL_NUM_THREADS=1`,
  `CUDA_VISIBLE_DEVICES`, `PF_LAUNCH_RANK`, `PF_LAUNCH_NRANKS`, `PF_LAUNCH_CPU`, `PF_CORE`; nice from the
  site file.
- **Launchers.** One rank: plain exec (pf-launch stays as the parent to hold the leases and write the
  receipt). Several ranks: `mpirun`. Inside Slurm: `srun`. `--launcher` overrides this; `--launcher exec`
  with several cores runs one process pinned to all of them (builds).
- **Execution.** `--execution site` (default) applies the site prefix: run-frozen on zenobia, a container
  command elsewhere. `--execution host` runs directly; `--prefix 'CMD'` sets a per-rank prefix for one
  run. When pf-launch itself runs inside the frozen root (`run-frozen python pf_launch.py ...`), it
  detects this and does not nest the sandbox.
- **Identity admission.** `strict`: every recorded value must equal the observed one (kernel release,
  NVIDIA driver version and module srcversion, the set of GPU UUIDs, CPU model, sha256 of the frozen root
  manifest), otherwise exit 78. `record-only`: values and mismatches go into the receipt only.

### OpenMPI binding (why `--bind-to none` plus a per-rank wrapper)

For several ranks pf-launch runs
`mpirun --bind-to none -np N PYTHON pf_launch.py --rank-exec PLAN -- PROGRAM ARGS`. The launch is
pinned to the union of the selected CPUs at the site nice level, so mpirun and its `prte` daemon stay on
those cores too. Each rank's wrapper reads its rank from `OMPI_COMM_WORLD_RANK` / `PMIX_RANK` /
`PMI_RANK` / `SLURM_PROCID`. It pins itself to that rank's one CPU with `sched_setaffinity` (the same
effect as `taskset`), sets nice and the environment, and starts the program as a child. The child's
parent-death signal is set, signals are forwarded, and the wrapper records the observed affinity, nice,
`CUDA_VISIBLE_DEVICES` and exit code for the receipt.

This was chosen over `--cpu-set` / `--map-by :PE-LIST=` or a rankfile for three reasons:

- **Exact rank-to-CPU map.** The mapping follows the requested order exactly, including non-contiguous
  lists and lists that start with a higher CPU (`--cpus 7,6` puts rank 0 on CPU 7). Each rank gets
  exactly one logical CPU, never the whole core (`--bind-to core` binds to all hardware threads of a
  core). Nothing depends on how a given Open MPI release orders a PE list or numbers rankfile slots
  (PRRTE, Open MPI 5.0.11 in the frozen root and on the host).
- **Same path for every launcher.** The same wrapper serves mpirun and srun, so the rank-to-GPU logic
  and the receipt reports are shared.
- **Sandbox constraint.** run-frozen (bwrap) gives each sandbox a private `/tmp` and PID namespace.
  Per-rank sandboxes could therefore not reach the PMIx server, so mpirun itself must run inside one
  sandbox (`mpi_inside_prefix: true`). The wrapper approach works unchanged there.

Validated on zenobia with the frozen root's mpirun and with the host mpirun: MPI_Init and an Allreduce
succeed through the wrapper, ranks observe affinity {6} and {7}, and `prte` and bwrap are confined to
CPUs 6-7 at nice 15.

## Receipt

Every real run writes an execution envelope receipt (`--receipt PATH`, else `receipt_dir`).
`--dry-run --receipt PATH` writes the same structure with no times or exit codes, and `--dry-run --json`
prints it. The top-level fields are exactly:

`host` (name, site, kernel, CPU model, topology summary, identity policy and checks), `site_file_digest`
(path, sha256), `selected_cores` (request, CPUs, physical cores, lease files and leases held,
reservations with probe results, cores leased elsewhere, Slurm variables, nice), `selected_gpus`
(request, UUIDs, ranks per GPU, leases), `rank_count`, `rank_to_core` (per rank: CPUs, physical core,
SMT siblings, binding method, observed affinity/nice/`CUDA_VISIBLE_DEVICES`/exit code), `rank_to_gpu`,
`gpus` (index, UUID, name, compute capability, memory, driver, PCI bus, NUMA node), `launcher_argv`
(pf-launch argv, version and sha256, launcher, full child argv, cwd), `environment_digest` (sha256 of the
launch environment plus the variables pf-launch set), `root_or_image_digest` (frozen root manifest sha256
and run-frozen sha256, or container image digest), `start_time`, `end_time`, `exit_codes` (status,
pf-launch exit, launcher exit, per-rank exit codes, messages).

Exit codes: the program's exit code (128+signal if killed); 64 malformed request (bad list, SMT
siblings, too many GPUs for the ranks); 69 requested CPU/GPU absent; 70 the program could not be
started; 75 reserved or leased; 78 site file problem or identity admission failure.

## Limitations and open items

- mpirun mode is single-node; multi-node runs go through Slurm/srun. A hostfile mode is not implemented.
- Under srun, the execution prefix is applied per rank (container hybrid model). A bwrap frozen root
  per rank under srun is untested; on clusters use the container image.
- Under Slurm, identity admission runs on the batch node only. Per-node admission belongs in the
  program's own preflight or a prolog.
- GPU-to-core NUMA locality is recorded (GPU `numa`), not enforced; order `core_preference` for it.
- The pf-launch process itself is neither pinned nor niced; it only waits on the child. While it waits,
  its children hold the lease file descriptors as well, so the leases stay held if pf-launch is killed.
- On zenobia the simqueue probe runs `simq active`. Inside the frozen sandbox the queue database is
  hidden, and the probe then reports cores 0-3 reserved (fail-safe). The static reservation of cores 0-5
  makes that probe informational only.
