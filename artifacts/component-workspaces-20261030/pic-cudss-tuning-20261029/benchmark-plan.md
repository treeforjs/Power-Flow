# Bounded cuDSS tuning plan for the integration chat

Preserve the manual hold recorded in `<workspace>/outputs/full60-manual-pause.json`. Only the integration chat executes GPU replays, with CPU6/nice15/one job and the shared testing-core.lock. Every trial uses a fresh copy of the same checkpoint and the harness that preserves pre-existing stopped state. No automatic resume/restart, live executable edit, precision/refinement change, solver skipping or dependency update is part of this plan.

## Why this sweep

Pinned0.6 exposes only the default solve algorithm. The documented low-cost ordering alternatives are customized METIS nested dissection with ND_NLEVELS (default512, recommended nearby power-of-two values), and AMD/ALG_3. Factorization default is recommended; ALG_1 is not a first sweep. Types/release notes disagree in wording about ALG_1/2 symmetric support; neither is needed for this SPD experiment. No later superpanel or deterministic-mode API is present. [NVIDIA0.6 types](https://docs.nvidia.com/cuda/archive/12.9.1/cudss/types.html).

Hybrid execution is a separate CPU/GPU placement heuristic for low-parallelism work. Try it only after ordering, with one host thread and device-resident inputs. Hybrid memory is designed to fit otherwise-too-large factors and adds transfers; leave it disabled. [NVIDIA0.6 advanced features](https://docs.nvidia.com/cuda/archive/12.9.1/cudss/advanced_features.html).

The baseline trace's largest sparse forward/backward kernels launch3704 or68574 blocks; insufficient block count alone does not explain their cost. Their dependencies, fill, memory behavior and instruction efficiency remain unmeasured. The smaller TRSV variants launch17 blocks on80 SMs, so these individual launches cannot occupy every SM simultaneously, but together they account for only about8% of total kernel duration. Grid shape is not achieved occupancy. Reordering changes fill and dependency scheduling, which is the useful question beyond graph submission overhead. Actual factor fill and permutation have not been extracted from the existing baseline trace; this candidate adds those queries for the parent replay.

The setting named ND_NLEVELS is treated as an opaque library performance knob. Do not interpret documented512 as an observed elimination-tree depth. Actual permutation, LU_NNZ and memory-query results must be recorded before attributing a speed change to reduced fill or increased parallelism.

## Minimal sequence

1. **Inspection/default control:** run the default candidate on the real checkpoint with a fresh AUDIT_PREFIX and DUMP_MATRIX=1. Require successful outer receipt and unchanged scientific guards. Capture both system records, effective settings, fill, memory estimates, valid permutation and matrix-array hashes. Compare native arrays to the CPU reconstruction; do not assume equal shape proves equal values. Query failures are explicitly recorded and must not become zero-fill claims.
2. **Screening:** unprofiled short identical replays, one each for default ND128, ND256, and AMD. Keep hybrid execution0. Include an explicit default/512 control to detect binary/setup overhead. If one setting is obviously bad or fails existing guards/comparisons, stop that branch. ND1024 is the next point only if the first results justify broadening.
3. **Confirmation:** interleave at least three control/winner repetitions from the same seed/physical endpoint. Compare median and spread for advance time per accepted step, solve+copies per call, total process wall time, setup/analysis/factorization and resident-memory estimates. Disable AUDIT_PREFIX/DUMP_MATRIX in these timing runs to remove file/structure-analysis overhead. All runs must finish the same step/particle state within the unchanged comparison policy.
4. **Hybrid check:** one hybrid-execute1 trial on the best ordering, one CPU thread. Confirm only if it is promising; otherwise stop. Record that it changes compute placement/synchronization but leaves hybrid memory0 and FP64/two refinements fixed.
5. **Trace only the control and confirmed winner:** compare triangular-kernel durations/counts/shapes, transfer and synchronization costs. Use unprofiled receipts to decide performance. Do not broaden profiling or install tools before these simple variants show a reason.
6. **Integration:** apply only a demonstrated winner to a new parent-owned combination with the optimized CPU candidate, then repeat scientific comparisons and end-to-end timing. This tuning prefix deliberately retains sealed CPU code to isolate solver effects; it must not overwrite another worker's candidate.

Every numerical comparison needs explicit finite values; existing residual/charge/current guards; identical input clocks/particle IDs/weights; positions/velocities; sampled field/potential; histories/ledger values and reaction-free state consistency. Order changes can change roundoff, and cuDSS0.6 does not promise bitwise reproducibility. Byte mismatch alone is not corruption, but it does not prove equivalence. This direct candidate introduces no new tolerance or relaxed gate. Use the parent's established numerical criteria and retain all scientific guards.

## Gain versus complexity

The parent reports roughly51 ms per unoptimized advance with14 ms in solves, and roughly38 ms with the CPU optimization. If those solver costs stayed14 ms, a hypothetical2x solver improvement would change those totals to44 and31 ms: about16% and23% throughput gains respectively. These are arithmetic scenarios, not predictions or measurements of these settings. A fill/parallelism change is more relevant to the dominant device time than eliminating the small submission gaps, but its direction and size are unknown.

The implementation adds a bounded parser, two ordering settings, one placement flag and setup-only diagnostics; the solve body is byte-identical to the sealed source. This is a smaller experiment than graph lifetime/recovery code. A small stable improvement may therefore justify a simple ordering choice, but retain defaults if gains are below repeat variability or costs rise in memory/validation/maintainability. No speedup is claimed before the sweep.

Do not prioritize these structural changes yet: dropping isolated Dirichlet rows adds packing/reconstruction and affects only a few percent of input rows; sharing the static unit-bias factorization targets startup/memory rather than the two dependent half-step solves; batching those half-step RHSs would violate their sequential state dependency. A new iterative solver or mixed precision is a separate numerical-method project, not a hidden tuning option here.
