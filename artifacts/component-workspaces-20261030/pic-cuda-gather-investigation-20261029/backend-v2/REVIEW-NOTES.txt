F1: static upload ordering
set_snapshot marks static DMA in flight, performs the existing pageable uploads,
then checks cuCtxSynchronize BEFORE clearing that state or publishing metadata.
This occurs at setup/explicit refresh, never per particle or normal force step.
A failure closes/poisons the backend without publishing a new snapshot. The
resource owner knows that a context drain is needed before static buffers can
be released on that path. The underlying CUDA contract is documented at:
https://docs.nvidia.com/cuda/archive/12.8.1/cuda-driver-api/api-sync-behavior.html

F2: asynchronous lifetime and cleanup errors
One Resources owner outlives every submitted operation's buffers, module and
events. It closes on evaluate/refresh errors, normal explicit close, destructor,
and partial Impl-constructor unwind. While the correct context is current, it
attempts cuStreamSynchronize BEFORE destroying events/stream/module or freeing
pinned/device storage. A failed stream drain or pending static DMA triggers a
context-wide drain attempt. Original exceptions are rethrown unchanged.

If completion/context cannot be established, it does not free possibly-live
resources. It retains those allocations and its own primary-context reference,
records the failure, and requires the isolated candidate process to abort.
This intentional quarantine can leak until process/context-owner cleanup; it
avoids use-after-free. There is no reset/destroy of a borrowed/shared context.
Every failed cleanup API is kept in a fixed-capacity, allocation-free report
owned by the caller, or printed to stderr when no external sink was supplied.
Cleanup does not throw or replace the original operation error. Release failures
are retained/reported too, rather than converted to a success claim.

No extra per-step drain was added to successful evaluate. Its existing final
event remains the batch completion boundary. The new stream drain is shutdown
or error cleanup; the context fence is setup/refresh or error fallback. CUDA
stream lifetime contract:
https://docs.nvidia.com/cuda/archive/12.8.1/cuda-driver-api/group__CUDA__STREAM.html

Context contract
Default ContextPolicy::RequireCurrentSharedPrimary requires cuDSS-first setup:
there must already be a current context equal to device0's shared primary. It
retains and later releases only its own reference. It never creates a private
fallback and never resets/destroys a shared context. ContextPolicy::StandalonePrimary
is explicit API opt-in, only with no current context; the standalone CLI also
requires --standalone-primary. That path balances its retain/push/drain/pop/release.

A lost/wrong current context fails before force dispatch. Cleanup can temporarily
push the captured primary to drain/release the backend's resources, then restores
the caller's context. If activation fails, it quarantines rather than releasing
under an unrelated context. Wrong-thread cleanup is reported and quarantined.
Primary-context contract:
https://docs.nvidia.com/cuda/archive/12.8.1/cuda-driver-api/group__CUDA__PRIMARY__CTX.html
