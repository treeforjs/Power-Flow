1. DepositSupportBuilder on the device (HOST-WORK item 2: 1.6 ms per 1e3 carriers per iterate, k >= 2 iterates)
 Code: source/census_charge.hpp class DepositSupportBuilder (two build() overloads: census + endpoints; census + receipt with
 sinks/newborns), called per fixed-point iterate in prepare_closed_proposal (root_api.hpp for Owner, resident_owner.hpp for
 ResidentOwner) and through the endpoint continuity guard of Model::prepare / k_continuity (support_C per node).
 What it computes per node n: absolute_C(n) = finish(s1, s2, m) with, over the carriers p whose start/end box (cell indices,
 widened by delta_d = eps (3 C_d + 8) cells) contains n: s1_n += t1_p = Q_p (2C + 14 + (16C + 67) R_p), s2_n += t2_p = Q_p R_p,
 m_n += 1; Q_p = magnitude(Words(w) * q) (long double), R_p = sum_d |b_d - a_d| + 2 delta_d (long double), C = nx + ny + nz.
 The rule text endpoint_tolerance_rule (field_model.hpp) is in the configuration identity.
 The design question: t1, t2 are long double and s1, s2 are x87 sums in ascending carrier-ID order (8..27 nodes per carrier).
 A device kernel cannot reproduce x87 roundings. Two consistent choices:
  (a) same results: keep the x87 host form (no gain), or prove that a device form rounds to the same binary64 absolute_C for
      every input (not provable in general: the sums are long chains);
  (b) documented identity change (recommended): define t1, t2 as exactly specified binary64/double-word values (e.g. the
      products formed with fma two-products, the result rounded UP) and s1, s2 as EXACT sums (native v7 forms
      pf_v7::ExactSum / device Forms::sum_products-style superaccumulator; emit (node, term) records per carrier from the push's
      device arrays, sort by node, segmented exact sums; order- and partition-independent, CPU = GPU bit for bit), then
      finish() in a stated binary64 order rounded upward. The bound is a tolerance, not state: the change of its values is
      bounded by a few ulps; state it, bind the new rule text into the configuration identity, and show the continuity guard
      decisions are unchanged on the v3.3 fixtures (parity-coupled, dense blobs, sinks, newborns).
 Inputs on the device already: carriers (SoA) and endpoints / sink hit points in the GPU push engine
 (gpu/hall_gpu_push_v3.cpp MotionEngineV3: carriers buffer, outs = endpoint/start/disp arrays, sink outputs); the resident field
 engine (gpu/resident_field.cpp) shares the hall_gpu::Session, so the support array can stay on the device and be read by
 k_continuity (ctx.support) without a host round trip. Newborns start at the birth point; sinks end at the hit point.
2. The 4-6x slowdown (v3.1 RESULTS section 5)
 DepositSupportBuilder took 2.84 ms at 1e4 carriers in the resident test process against 0.64 ms in the baseline profiler
 process with the same code and data; repeated calls are equal (not a warm-up). Not explained. Known differences: the
 resident process holds a CUDA context, the device field and the GPU push engine, and every run is pinned to ONE leased core
 (taskset), so the CUDA driver's helper threads share that core with the host loop; the baseline process had no device
 context. Code, data, allocation pattern (three nn-sized vectors per call) and x87 arithmetic are identical. Candidates to
 test first: driver threads / spin-wait synchronisation on the single pinned core (cudaDeviceScheduleBlockingSync; perf sched),
 frequency of the leased core under the GPU process, cache pollution by the pinned staging buffers. Moving the builder to the
 device removes the symptom but the cause also affects every other host loop of the resident process.

 (motion(), trial_E/B(), current_A_m(), field_heat()), checkpoint save/restore (bit-identical continuation), native v7 forms.
 To run the coupled path through it: (i) the coordinator templates its step and adapters on the owner type (the protocol

 accessors the coordinator uses (field(), charge(), candidate_field/charge(), Owner::save/restore) with accepted_state() /
 candidate_state() downloads (diagnostic only) and ResidentOwner::save/restore; (iii) use the GPU motion provider
 (gpu_backends.hpp GpuMotionProvider) on the same Device; (iv) remaining host work per iterate in the resident closed proposal:
